# 9주차 실습 — 보안시스템

## 1. 학습 목표

- IDS/IPS(Suricata)의 동작 원리와 룰 문법을 이해한다.
- **3주차에 캡처한 pcap을 재생**해 실제 공격 트래픽을 탐지할 수 있다.
- 커스텀 탐지 룰을 작성하고 **오탐(false positive)을 튜닝**할 수 있다.

## 2. 사전 준비물

- Docker (`starter/suricata/docker-compose.yml`: Suricata + 룰 디렉터리 마운트)
- 입력 자산: **3주차 `login-plaintext.pcapng`** (없으면 강의 제공 백업 pcap 사용)
- 도구: Suricata, `jq`(로그 파싱)
- 선행 지식: 3주차 네트워크 개념

## 3. 수업 중 랩 (80분)

> 스타터: `starter/suricata/` (docker-compose + `rules/local.rules` 스타터)

**Step 0.** 프로젝트 루트에서 제출 폴더를 만든다.
```bash
cd /path/to/workISTutorial
mkdir -p week09
```

### Lab 9-A. pcap 준비 (10분)

**Step 1.** 3주차에서 캡처한 pcap을 분석 폴더에 `login-plaintext.pcapng` 이름으로 넣는다.
3주차 캡처 파일명이 다르면(예: `login-post-dump.pcapng`) 복사하며 이름을 맞춘다.
```bash
mkdir -p starter/suricata/pcaps starter/suricata/logs
# 3주차 캡처(파일명은 자신의 것에 맞게) → 분석 폴더에 login-plaintext.pcapng 로 복사
cp week03/login-post-dump.pcapng starter/suricata/pcaps/login-plaintext.pcapng
ls -la starter/suricata/pcaps/login-plaintext.pcapng
```
> 3주차 캡처가 없으면 조교 배포 백업본을 같은 이름으로 넣는다.

### Lab 9-B. Suricata로 pcap 재생 (30분)

**Step 2.** compose의 `run`으로 오프라인 분석을 실행한다.
```bash
docker compose -f starter/suricata/docker-compose.yml run --rm suricata \
  -r /pcaps/login-plaintext.pcapng -l /var/log/suricata -S /rules/local.rules -k none
```

**Step 3.** `eve.json`에서 탐지 이벤트(예시 룰 `sid:1000001`)를 확인한다.
```bash
jq -c 'select(.event_type=="alert") | {sig: .alert.signature, sid: .alert.signature_id}' \
  starter/suricata/logs/eve.json | sort | uniq -c
# 기대: "ShopGuard plaintext login POST" (sid 1000001) 이 1건 이상 탐지된다.
```
> 아무 alert 도 안 나오면: pcap 경로/이름 확인, `-S /rules/local.rules` 적용 여부,
> `eve.json` 이 `starter/suricata/logs/` 에 생성됐는지 확인한다.

### Lab 9-C. 룰 구조 해부 + 매칭 확인 (40분)

**Step 4.** `rules/local.rules`의 예시 룰을 열어 `action / header / options` 구조를 해부한다.
```
alert http any any -> any any (msg:"..."; flow:to_server; http.method; content:"POST"; \
      http.uri; content:"/login"; classtype:policy-violation; sid:1000001; rev:1;)
#  └action └────header────┘  └──────────────── options ─────────────────────┘
```

**Step 5.** 룰의 `msg`를 살짝 바꿔 다시 재생(Step 2)한 뒤, 바뀐 메시지로 매칭되는지 확인한다.

**랩 제출물**: Step 3 탐지 이벤트(eve.json 발췌) + Step 5 커스텀 룰 매칭 캡처.

## 4. 주간 과제 (2.5시간)

### 과제 1. 커스텀 룰 3종 작성
SQLi·포트스캔·브루트포스를 탐지하는 룰을 작성하고 pcap 재생으로 검증한다.
전체 룰은 `week09/local.rules` 참고(그대로 복사해 쓸 수 있다).

**Step 1-1. 검증용 공격 pcap을 생성한다.**
커스텀 룰이 매칭될 **공격 트래픽 pcap**이 필요하다. 아래 헬퍼가 sudo 없이 Docker로
SQLi(URI)·로그인 브루트포스·포트스캔 트래픽을 만들어 `pcaps/attack.pcap` 으로 저장한다.
```bash
bash starter/suricata/make-attack-pcap.sh
# → starter/suricata/pcaps/attack.pcap 생성
```

**Step 1-2. 커스텀 룰 3종을 `rules/local.rules` 에 추가한다**(복사·붙여넣기).
```
# [1] SQLi 시도 — URI에서 ' OR 1=1 / UNION SELECT (대소문자·공백 유연).
#     http.uri 버퍼는 Suricata가 URL 디코드·정규화하므로 인코딩 페이로드도 잡힌다.
alert http any any -> any any (msg:"ShopGuard SQLi attempt"; flow:to_server; \
  http.uri; pcre:"/('|%27)?\s*(OR\s+1=1|UNION\s+SELECT)/i"; \
  classtype:web-application-attack; sid:1000002; rev:1;)

# [2] 포트 스캔 — 5초 내 같은 출발지에서 SYN 20개 초과(임계 초과분만 알림).
alert tcp any any -> any any (msg:"ShopGuard portscan (SYN flood from single src)"; \
  flags:S; detection_filter:track by_src, count 20, seconds 5; \
  classtype:attempted-recon; sid:1000003; rev:1;)

# [3] 로그인 브루트포스 — 30초 내 같은 출발지의 /login POST 10회 초과.
alert http any any -> any any (msg:"ShopGuard login bruteforce"; flow:to_server; \
  http.method; content:"POST"; http.uri; content:"/login"; \
  threshold:type threshold, track by_src, count 10, seconds 30; \
  classtype:attempted-user; sid:1000004; rev:1;)
```
또는 완성본을 그대로 복사한다:
```bash
cp week09/local.rules starter/suricata/rules/local.rules
```

**Step 1-3. 공격 pcap을 재생해 3종이 모두 탐지되는지 확인한다.**
```bash
rm -f starter/suricata/logs/eve.json
docker compose -f starter/suricata/docker-compose.yml run --rm suricata \
  -r /pcaps/attack.pcap -l /var/log/suricata -S /rules/local.rules -k none

jq -c 'select(.event_type=="alert") | {sig:.alert.signature, sid:.alert.signature_id}' \
  starter/suricata/logs/eve.json | sort | uniq -c
```
기대 출력(건수는 환경마다 다를 수 있음):
```
   2 {"sig":"ShopGuard SQLi attempt","sid":1000002}          # OR 1=1, UNION SELECT 각 1건
  38 {"sig":"ShopGuard portscan (SYN flood ...)","sid":1000003}
   1 {"sig":"ShopGuard login bruteforce","sid":1000004}
```

**Step 1-4. 룰 문법을 해부해 보고서에 남긴다.**
- `pcre:"/.../i"` — 대소문자 무시 정규식. SQLi의 다양한 표기를 한 룰로 커버.
- `detection_filter:track by_src, count 20, seconds 5` — 출발지별 임계 초과 패킷마다 알림(스캔에 적합).
- `threshold:type threshold, track by_src, count 10, seconds 30` — 임계 넘는 순간 1건만 알림(브루트포스에 적합).

### 과제 2. 오탐 튜닝
정상 트래픽에서 발생하는 **오탐(false positive)** 을 찾아 완화하고, 전/후 건수를 비교한다.

**Step 2-1. 정상 pcap으로 재생해 오탐을 관찰한다.**
Lab 9-A에서 넣은 정상 로그인 pcap(`login-plaintext.pcapng`)으로 3종 룰을 돌려본다.
```bash
rm -f starter/suricata/logs/eve.json
docker compose -f starter/suricata/docker-compose.yml run --rm suricata \
  -r /pcaps/login-plaintext.pcapng -l /var/log/suricata -S /rules/local.rules -k none

# 룰별 탐지 건수
jq -c 'select(.event_type=="alert") | .alert.signature_id' \
  starter/suricata/logs/eve.json | sort | uniq -c
```
> 실측 예: 포트스캔 룰(sid 1000003)이 **수만 건** 폭증한다. 정상 트래픽에는 SYN 패킷이
> 매우 많은데(연결마다 SYN), `flags:S` + 카운트 임계 방식이 이를 전부 "스캔"으로 오인하기
> 때문이다. **이것이 대표적 오탐**이며, SQLi(1000002)/브루트포스(1000004)는 정상 pcap에
> 공격 패턴이 없으므로 뜨지 않는다.

**Step 2-2. 오탐의 원인을 분석하고 룰을 완화한다.**
근본 원인: `detection_filter`는 **패킷 수**만 세고 "서로 다른 목적지 포트 수"는 못 센다 →
연결이 많은 정상 호스트와 스캐너를 구분하지 못한다. 완화 방향(택1 이상):
```
# (a) 임계를 크게 올리고 시간 창을 좁혀 '짧은 폭주'만 잡는다
alert tcp any any -> any any (msg:"ShopGuard portscan (tuned)"; flags:S; \
  detection_filter:track by_src, count 100, seconds 2; \
  classtype:attempted-recon; sid:1000003; rev:2;)

# (b) 외부→내부 방향으로 한정해 내부 정상 트래픽을 제외
#     (HOME_NET/EXTERNAL_NET 은 suricata.yaml 에서 자기 대역에 맞게 정의)
alert tcp $EXTERNAL_NET any -> $HOME_NET any (msg:"ShopGuard portscan (scoped)"; flags:S; \
  detection_filter:track by_src, count 50, seconds 3; \
  classtype:attempted-recon; sid:1000003; rev:3;)
```
> 완전 제거가 어려우면, 이 한계 자체(카운트 기반 SYN 탐지의 근본적 노이즈)를 보고서에
> 분석으로 남긴다 — Suricata의 전용 스캔 탐지나 목적지 포트 다양성 추적이 필요하다는 결론.

**Step 2-3. 같은 정상 pcap으로 재재생해 전/후 건수를 비교한다.**
```bash
rm -f starter/suricata/logs/eve.json
docker compose -f starter/suricata/docker-compose.yml run --rm suricata \
  -r /pcaps/login-plaintext.pcapng -l /var/log/suricata -S /rules/local.rules -k none
jq -c 'select(.event_type=="alert") | .alert.signature_id' \
  starter/suricata/logs/eve.json | sort | uniq -c
```
전/후 건수를 표로 정리한다(예: `sid 1000003: 42,000+ → N건`). 튜닝 후에도 공격 pcap
(`attack.pcap`)에서는 스캔이 여전히 탐지되는지 함께 확인해 **탐지력과 오탐의 트레이드오프**를 논한다.

## 7. 흔한 오류 / 확장 과제

**흔한 오류**
- `sid` 중복 또는 미지정으로 룰 로드 실패 → 고유 sid 사용.
- 룰이 너무 광범위(`content:"SELECT"`)해 오탐 폭증 → 문맥(`http.uri`, `nocase`) 한정.

**확장 과제 (심화)**
- IPS 모드(inline drop)로 전환해 탐지가 아닌 **차단**을 시연한다.
- Suricata `eve.json`을 ELK/OpenSearch로 수집해 **대시보드**로 이상 패턴을 시각화한다.
