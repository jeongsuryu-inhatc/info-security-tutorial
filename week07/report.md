# week07 — 암호의 이해 리포트

> 산출: `classic.js`(고전암호), `migrate-bcrypt.js`(해시 마이그레이션), `aes.js`(AES-GCM)

## 1. 고전 암호 크래킹 (Caesar/Vigenère)

- **Caesar**: 키 공간이 25개뿐 → **전수 대입(brute force)** 으로 즉시 해독.
  ```bash
  # 26개 시프트를 모두 출력해 사람이 읽히는 줄의 shift 가 정답 키
  ```
- **Vigenère**: 반복 키로 단일 시프트 약점을 가리지만, **Kasiski/빈도분석**으로 키 길이 추정 후
  각 위치를 Caesar 로 분해 → 해독.
- **원리(빈도분석)**: 자연어의 글자 빈도(예: 영어 E, 한국어 조사 패턴)가 암호문에 그대로 보존되어,
  치환/시프트 암호는 통계로 무너진다.
- **교훈**: 키 공간이 작거나 평문 통계가 보존되면 암호는 안전하지 않다 → 현대 대칭키(AES)가 필요.

## 2. bcrypt 마이그레이션 (평문 → 해시)

`migrate-bcrypt.js` 로 `shopguard.sqlite` 의 평문 비밀번호를 bcrypt 해시로 일괄 변환(실측).

- **결과**: `root123/alice1234/bobpass` → 모두 `$2b$12$…` 로 변환.
- **멱등성**: 이미 `$2[aby]$` 접두사면 건너뜀 → 재실행 시 "변환 0건, 건너뜀 3건"(이중 해싱 방지).
- **로그인 검증**: `bcrypt.compareSync('alice1234', hash)` → **true**, 오답 → **false**.

### cost 벤치마크 (실측)

| cost | 해시 1건 시간 |
|---|---|
| 10 | 약 70 ms |
| 12 | 약 250 ms |

> cost(작업계수)가 1 오르면 연산량이 2배. cost 12 는 10 대비 **약 3~4배 느리다**.
> 느릴수록 **무차별 대입 비용이 커져** 안전하지만, 로그인 지연과 균형을 맞춰 10~12 를 택한다.

## 3. AES-256-GCM (기밀성 + 무결성)

`aes.js` — 전화번호 등 민감정보 암복호화(실측).

- **왕복**: `010-1234-5678` → 암호화 → 복호화로 원문 복원.
- **랜덤 IV**: 같은 평문을 두 번 암호화해도 **암호문이 서로 다름**(IV 재사용 금지 준수).
- **무결성**: 인증 태그 1바이트 변조 → 복호화가 예외(`Unsupported state or unable to authenticate data`)로 실패 → **위·변조 탐지**.
- **키 관리**: 키는 하드코딩 금지, 환경변수 `SHOPGUARD_KEY`(32바이트) 로 주입.

## 4. 해시 vs 암호화 (핵심 구분)

| | 해시(bcrypt) | 암호화(AES-GCM) |
|---|---|---|
| 방향 | **단방향**(복호화 불가) | 양방향(키로 복호화) |
| 용도 | 비밀번호 저장·검증 | 민감정보 저장·전송(원문 필요) |
| 검증 | `compare(입력, 해시)` | `decrypt` 후 사용 |

> 흔한 오류: 비밀번호를 AES 로 "암호화 저장" → 잘못. 비밀번호는 **복호화 불가능한 해시**로 저장한다.
> IV 고정/재사용은 GCM 에서 치명적 → 매 암호화마다 랜덤 IV.
